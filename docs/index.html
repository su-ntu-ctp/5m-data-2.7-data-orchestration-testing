🔍 Data Testing Guide

Master data quality with Great Expectations & DBT Testing

📚 What is Data Testing?

Data testing is an important part of data quality management. It verifies that data satisfies expected properties.

🧠 In Plain English

Think of a factory quality inspector checking products before they leave the line. Data testing does the same job for your data: before (or after) it moves through your pipeline, you check it against a set of rules — "no missing values," "dates must be real dates," "prices can't be negative" — and reject or flag anything that fails.

You never fully trust data just because it "loaded successfully." Loading without errors only means the file was readable — it says nothing about whether the numbers inside make sense.

Also known as: Data validation, data quality assurance, data quality control, data quality assessment

🧩 Glossary — Terms You'll See in This Lesson

No prior data engineering knowledge assumed. Skim these once, then refer back whenever a term feels unfamiliar.

Pipeline
The series of automated steps that moves data from a source (e.g. a CSV file, an API) into a place where it can be analysed, transforming it along the way.
ETL / ELT
Extract, Transform/Load, Load/Transform — the order in which you pull data out, reshape it, and store it. Modern warehouses usually load raw data first, then transform it (ELT).
Data Warehouse
A database built for analysis rather than day-to-day transactions — where your cleaned, testable data ends up living (e.g. BigQuery, Snowflake).
Schema
The "shape" of your data: which columns exist, what data type each one is (text, number, date), and how tables relate to each other.
Expectation / Assertion
A single rule you expect your data to follow, e.g. "column age is always between 0 and 120." The core building block in Great Expectations.
Test
DBT's word for the same idea — a check that either passes or fails against your data. A dbt test is really just an expectation written as SQL.
Model (dbt)
A saved SQL query that dbt turns into a table or view in your warehouse — the "transform" step of your pipeline.
Orchestration
Automatically running your pipeline's steps in the right order, on a schedule, and alerting you when something breaks — instead of running scripts by hand.
DAG
"Directed Acyclic Graph" — a fancy name for a flowchart of tasks where each task points to the ones that must run after it, with no loops.

📋 Core Concepts

🧠 In Plain English

Great Expectations organises everything around one question: "where is my data, and what rules should it follow?" The four concepts below build on each other like nested boxes:

Data Context (the project folder) → Data Source (the address of your data) → Data Asset (a named table/file within that address) → Batch Definition (exactly which slice of that asset you want to check right now).

1. Data Context

Defines storage location for metadata, configurations, and validation results

🧠 In Plain English

The Data Context is your GX "project folder" — it remembers every Data Source, rule, and past test result so you don't have to redeclare them each time.

💡 All GX scripts start with creating a Data Context
context = gx.get_context()

2. Data Sources

Tell GX where your data is located and how to connect to it

🧠 In Plain English

A Data Source is just an address — "my CSV files live in this folder" or "my tables live in this database." GX needs this address before it can read anything.

Amazon S3 Azure Blob Google Cloud Local Files 
source_folder = "data/"
data_source_name = "resale_flat"

data_source = context.data_sources.add_pandas_filesystem(
    name=data_source_name, 
    base_directory=source_folder
)

3. Data Assets

A collection of related records within a Data Source

🧠 In Plain English

If the Data Source is the folder's address, the Data Asset is the specific file or table you actually care about inside it — e.g. "the CSV files that hold resale flat prices."

asset_name = "resale_csv_files"
file_csv_asset = data_source.add_csv_asset(name=asset_name)

4. Batch Definition

Request all records or a subset from a Data Asset

🧠 In Plain English

A Batch Definition says "when I run a test, grab this slice of the asset" — one file, one date range, or the whole thing. The actual data you get back is called a Batch.

batch_definition = file_data_asset.add_batch_definition_path(
    name="resale_flat_201701_202306.csv",
    path="resale_flat_201701_202306.csv"
)

batch = batch_definition.get_batch()

✅ Creating Expectations

🧠 In Plain English

An Expectation is one rule ("this column's max value should be under 2020"). A Suite is a checklist that bundles several rules together. A Validation Definition pairs that checklist with a specific Batch of data and remembers the pairing so you can re-run it anytime. Running it produces Validation Results — the report card telling you which rules passed or failed.

Single Expectation

preset_expectation = gx.expectations.ExpectColumnMaxToBeBetween(
    column="lease_commence_date",
    min_value=1,
    max_value=2020
)

validation_results = batch.validate(preset_expectation)

Expectation Suite

💡 Group multiple expectations together for comprehensive validation
suite_name = "sctp_expectation_suite"
suite = gx.ExpectationSuite(name=suite_name)
suite = context.suites.add(suite)
suite.add_expectation(preset_expectation)

Validation Definition

definition_name = "sctp_validation_definition"
validation_definition = gx.ValidationDefinition(
    data=batch_definition,
    suite=suite,
    name=definition_name
)

validation_results = validation_definition.run()

🚦 Checkpoints

A Checkpoint executes one or more Validation Definitions and then performs a set of Actions based on the results — the piece that automates the "run this and alert on failure" step in a real pipeline.

🧠 In Plain English

Everything above (Context → Source → Asset → Batch → Expectation → Suite → Validation Definition) is the setup. A Checkpoint is the "run button" you'd actually schedule in production — it runs your Validation Definition(s) and can trigger an action (e.g. send a Slack alert) when data fails.

🚀 DBT Testing Setup

DBT provides built-in tests and can be extended with powerful testing packages

🧠 In Plain English

dbt ("data build tool") lets you write your transformations as plain SQL SELECT statements, and it handles running them in the right order inside your warehouse. Because your transformations are just SQL, dbt can also run SQL-based tests against the results — the same idea as a GX Expectation, just written as a query that should return zero bad rows instead of a Python rule.

📦 Installing dbt_utils

🧠 In Plain English

dbt only ships four basic tests out of the box. Packages like dbt_utils are community-built add-ons (think: browser extensions) that give you many more ready-made test types, so you don't have to hand-write complex SQL yourself.

packages:
  - package: dbt-labs/dbt_utils
    version: 1.3.3

Create this file in your DBT project root directory

dbt deps

This will download and install the dbt_utils package

✅ dbt_utils Tests

accepted_range Test

Check if values are within an acceptable range

- name: date
  tests:
    - dbt_utils.accepted_range:
        arguments:
          min_value: "PARSE_DATE('%F', '2012-01-01')"
          max_value: "CURRENT_DATE()"
💡 Great for validating date ranges or numeric boundaries
dbt-core 1.10+ requires test arguments to be nested under an arguments: key — the test still fails/is skipped silently on older syntax.
🧠 Try It Yourself

In models/star/schema.yml, the pack and bottle_volume_ml columns use this same test with min_value/max_value left as placeholders. Run a SQL query to find the real min/max for each column, then fill them in — that's the exercise.

expression_is_true Test

Validate complex business logic across multiple columns

tests:
  - dbt_utils.expression_is_true:
      arguments:
        expression: "ROUND(sale_dollars, 1) = TRUNC(bottles_sold * state_bottle_retail, 1)"
        severity: error # accepts only `error` and `warn`, default is error
💡 This is a model-level test - place it outside the columns section

📦 Installing dbt-expectations

🧠 In Plain English

dbt-expectations is another add-on package, this time inspired directly by Great Expectations — it ports many of GX's statistical and pattern-matching rules into dbt's SQL-test world, so both tools end up speaking a similar "rules" vocabulary.

packages:
  - package: dbt-labs/dbt_utils
    version: 1.3.3
  - package: metaplane/dbt_expectations
    version: 0.10.10

Add dbt-expectations to your packages file

dbt deps

⚙️ Orchestration with Dagster

Automate and schedule your data testing workflows with orchestration tools

🧠 In Plain English

Imagine baking a cake: you must mix the batter before baking, and bake before icing — running steps out of order ruins the cake. An orchestrator like Dagster is the recipe manager for your data pipeline. It knows which step depends on which, runs them in the correct order automatically on a schedule (e.g. every night at midnight), and tells you the moment a step fails — instead of you running scripts by hand and hoping nothing broke.

🚀 Why Orchestration?

Orchestration allows you to automate your data pipelines, schedule testing workflows, manage dependencies, and monitor data quality continuously in production environments.

🧠 In Plain English

A job is one runnable pipeline (a group of steps). An op is a single step inside that job (e.g. "extract," "validate," "transform"). A schedule tells Dagster when to run the job automatically, using the same cron syntax you'd see in any Unix scheduler (e.g. 0 0 * * * = every day at midnight).

📦 Dagster for Data Testing

💡 Dagster orchestrates Meltano and DBT as ordinary CLI commands, wrapped as Dagster assets via Pipes for full logging and observability
🧠 In Plain English

Dagster doesn't need a special "Meltano plugin" — PipesSubprocessClient just runs any shell command (meltano run ..., dbt build) as a step in your pipeline, and streams its logs back into the Dagster UI. @asset(deps=[...]) is how you say "this step only runs after that one finishes."

Sample Dagster Configuration — assets.py

# assets.py
from dagster import asset, AssetExecutionContext, PipesSubprocessClient

@asset
def pipeline_meltano(context: AssetExecutionContext, pipes_subprocess_client: PipesSubprocessClient):
    """Runs meltano using Dagster Pipes for better logging and observability."""
    return pipes_subprocess_client.run(
        command=["meltano", "run", "tap-postgres", "target-bigquery"],
        context=context,
        cwd="/path/to/your/folder/meltano_resale_in_lesson_2_6"
    ).get_results()

@asset(deps=[pipeline_meltano])
def pipeline_dbt_run(context: AssetExecutionContext, pipes_subprocess_client: PipesSubprocessClient):
    """Runs dbt build using Dagster Pipes."""
    return pipes_subprocess_client.run(
        command=["dbt", "build"],
        context=context,
        cwd="/path/to/your/folder/resale_flat_in_lesson_2_6"
    ).get_results()

From meltano-orchestration/meltano_orchestration/assets.py — swap the cwd paths for your own Meltano and dbt project folders from Unit 2.6.

🔄 Orchestrated Testing Workflow

This is exactly how extra/dagster_orchestration_dbt wires up its dbt_pipeline job — three assets chained with deps=[...], each shelling out to one dbt command.

🧠 In Plain English

deps=[pipeline_dbt_seed] is Dagster's way of saying "don't start this step until that one succeeds." Chain three assets like this and you get seed → run → test running in strict order, automatically, with each step's pass/fail visible in the Dagster UI.

1

Seed Reference Data

@asset
def pipeline_dbt_seed() -> None:
    """Runs dbt seed"""
    cmd = ["dbt", "seed"]
    output = subprocess.check_output(cmd, stderr=subprocess.STDOUT).decode()

Load static seed CSVs into the warehouse first

2

Run DBT Transformations

@asset(deps=[pipeline_dbt_seed])
def pipeline_dbt_run() -> None:
    """Runs dbt run"""
    cmd = ["dbt", "run"]
    output = subprocess.check_output(cmd, stderr=subprocess.STDOUT).decode()

Transform data using dbt models — only after seeding succeeds

3

Execute DBT Tests

@asset(deps=[pipeline_dbt_run])
def pipeline_dbt_test() -> None:
    """Runs dbt test"""
    cmd = ["dbt", "test"]
    output = subprocess.check_output(cmd, stderr=subprocess.STDOUT).decode()

Run all dbt tests to validate the transformations — only after the run succeeds

4

Group Into a Job & Schedule

dbt_pipeline_job = define_asset_job(
    name="dbt_pipeline",
    selection=["pipeline_dbt_seed", "pipeline_dbt_run", "pipeline_dbt_test"]
)
dbt_pipeline_schedule = ScheduleDefinition(
    job=dbt_pipeline_job, cron_schedule="0 0 * * *"  # every day at midnight
)

Bundle the three assets into a job, and the job's run history is where you monitor pass/fail and set up alerts

📊 Dagster Configuration Example

🧠 In Plain English

When a whole dbt project should become Dagster assets automatically (one asset per model, with dbt's own dependency graph carried over), scaffold it with dagster-dbt project scaffold instead of hand-writing each asset — that's what resale_flat_dagster is.

from dagster import Definitions
from dagster_dbt import DbtCliResource
from .assets import resale_flat_dbt_assets
from .project import resale_flat_project
from .schedules import schedules, jobs

defs = Definitions(
    assets=[resale_flat_dbt_assets],
    schedules=schedules,
    jobs=jobs,
    resources={
        "dbt": DbtCliResource(project_dir=resale_flat_project),
    },
)

From resale_flat_dagster/resale_flat_dagster/definitions.py — resale_flat_dbt_assets is auto-generated by the scaffold, one Dagster asset per dbt model.

from dagster_dbt import build_schedule_from_dbt_selection
from .assets import resale_flat_dbt_assets

materialize_dbt_job_schedule = build_schedule_from_dbt_selection(
    [resale_flat_dbt_assets],
    job_name="materialize_dbt_models",
    cron_schedule="0 0 * * *",
    dbt_select="fqn:*",
)

materialize_dbt_job = materialize_dbt_job_schedule.job
schedules = [materialize_dbt_job_schedule]
jobs = [materialize_dbt_job]

From resale_flat_dagster/resale_flat_dagster/schedules.py — build_schedule_from_dbt_selection turns dbt's own model selection syntax straight into a Dagster schedule.

DAGSTER_DBT_PARSE_PROJECT_ON_LOAD=1 dagster dev

The env var tells Dagster to re-parse the dbt project on load, so newly added/changed dbt models show up as assets. Then use Materialize all under Lineage to trigger the dbt pipeline, and toggle the schedule on to run it automatically.

🔄 Complete Data Testing Workflow

Integrate both Great Expectations and DBT into your data pipeline

🧠 In Plain English

Neither tool replaces the other — they check different moments in the pipeline. GX is your gatekeeper at the front door: it checks raw, messy data the moment it arrives, before you trust it enough to transform. dbt tests are your gatekeeper at the back door: once dbt has transformed that raw data into clean tables, its tests confirm the transformation logic itself didn't introduce mistakes.

📋 Recommended Testing Strategy

Use Great Expectations for:

  • ✓ Raw data ingestion validation
  • ✓ File-based data sources
  • ✓ Complex statistical validations
  • ✓ Pre-transformation checks
  • ✓ Data quality monitoring

Use DBT Testing for:

  • ✓ Transformed data validation
  • ✓ Database table testing
  • ✓ Schema validation
  • ✓ Business logic verification
  • ✓ Integration testing
